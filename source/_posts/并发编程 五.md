### volatile原理

volatile 的底层实现原理是内存屏障，Memory Barrier

对 volatile 变量的写指令后会加入写屏障
对 volatile 变量的读指令后会加入读屏障

#### double-checked locking

饿汉式：类加载时就会导致该单例对象被创建

懒汉式：类加载时不会导致该单例对象被创建，而是首次使用该对象时才会创建

``` java
public final class SingleTon {  
private SingleTon() {  
}  
  
private static SingleTon INSTANCE = new SingleTon();  
  
public static SingleTon getInstance() {  
if (INSTANCE == null) { // 双重检查锁 目的是不需要每次调用的时候都加锁  
synchronized (SingleTon.class){  
if (INSTANCE == null) {  
INSTANCE = new SingleTon();  
}  
}  
}  
  
return INSTANCE;  
}  
}
```

以上代码的特点
1 懒惰实例化
2 首次使用sychronized才会加锁 后续不需要加锁
3 但是第一个Instance 是在同步代码块之外 有可能会发生代码重排


问题在于Java的内存模型（Java Memory Model, JMM）和指令重排序（Instruction Reorder）。当执行`INSTANCE = new SingleTon();`时，这个操作在JVM中可能被分解为以下三个步骤（在概念上）：

1. **分配内存**给`SingleTon`的实例（INSTANCE）。
    
2. **初始化`SingleTon`的构造器**。
    
3. 将`INSTANCE`引用指向分配的内存。
    

在Java中，步骤2和步骤3之间的顺序可能会被编译器和运行时优化，这意味着在没有适当同步的情况下，一个线程可能在步骤3之后但步骤2之前看到`INSTANCE`引用。如果此时另一个线程检查`INSTANCE`（非null），它可能会错误地认为`INSTANCE`已经完全初始化了，并尝试使用它，尽管实际上它的构造器可能还没有运行完毕。

也就是说 可能回将调用构造器的顺序和将分配内存的顺序反过来

## 无锁-乐观锁 （非阻塞） 

cas在使用时最好不要超过cpu核心数 否则上下文切换也会损耗资源 cas就是乐观锁

![[乐观锁_悲观锁.png]]

悲观锁认为自己在使用数据的时候一定有别的线程来修改数据，因此在获取数据的时候会先加锁，确保数据不会被别的线程修改。Java中，synchronized关键字和Lock的实现类都是悲观锁。

``` java 
public AtomicInteger balance;  
public void withdraw(Integer amount){  
while(true) {  
int prev = balance.get();  
int next = prev - amount;  
// 比较并设置 也就是cas  
if(balance.compareAndSet(prev, next)){  
break;  
}  
}  
}
```

AtomicInteger 的 updateAndGet原理

``` java

import java.util.concurrent.atomic.AtomicInteger;  
import java.util.function.IntUnaryOperator;  
  
public class Test34 {  
public static void main(String[] args) {  
AtomicInteger i = new AtomicInteger(0);  
  
int i1 = updateAndGet(i, x -> x + 1);  
}  
  
public static int updateAndGet(AtomicInteger i, IntUnaryOperator operator) {  
while (true){  
int prev = i.get();  
int next = operator.applyAsInt(prev);  
if (i.compareAndSet(prev, next)){  
return next;  
}else {  
System.out.println("retry");  
}  
}  
}  
}
```


AtomicReference<> 是对 引用类型进行原子操作的

ABA问题指的是，在CAS过程中 只能感知到共享变量的值和最初值A是否相同，无法感知到是否有其他线程对prev的值进行改动（A改为B再改为A）

AtomicStampedReference 就是为了感知到在ABA问题中 其他线程对值修改了多少次
AtomicMarkableReference 就是为了感知在ABA问题中 其他线程是否对值有修改
